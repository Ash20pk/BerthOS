# Gap analysis: `@berth/agents` vs. LangChain/LangGraph

Working list of concrete gaps found by auditing `packages/agents`, `packages/mesh-coordinator`/`mesh-daemon`, `packages/sdk`, and `packages/sdk-python` against LangChain/LangGraph's feature set (2026-08-04). Ranked by how quickly each would surface in a head-to-head technical evaluation. Status is updated as gaps get closed — see the progress log at the bottom for what changed and why.

Design constraint that shapes every "fixed" entry below: **no LangGraph-style node/edge graph DSL.** Where LangGraph would reach for a dedicated subsystem (a checkpointer, an interrupt primitive, a tracer), Berth's answer is to expose primitives the OS layer already has (Semantic FS, Context Bus, grants-server) to `@berth/agents`, rather than build a parallel one.

## Status key

- 🔴 Open — not started
- 🟡 Partial — some real progress, real scope left
- 🟢 Closed — done, verified (tests/build passing)

## Tier 1 — would lose a head-to-head immediately

| # | Gap | Status | Notes |
|---|-----|--------|-------|
| 1 | No state-graph/node-edge orchestration model | 🟡 Partial | **Closed for cycles/fan-out/branching (2026-08-04), branch `feat/crew-composable-functions`**: `Crew` gained `parallel`/`loopUntil`/`route` — same "just wiring over `Agent`" stance as the original three, not a graph DSL. `parallel(agents, {merge?})` fans out to every agent concurrently and combines outputs; `loopUntil({agent, until, maxIterations?})` is the cycle, feeding an agent's own output back in until a predicate fires or a turn cap is hit; `route({router, routes, fallback?})` is the conditional branch, an LLM classifying input to one of a fixed set of downstream agents. **Still open**: no explicit shared-state object threaded across steps (each function only ever passes a `string` along, same as the original three) — a LangGraph `StateGraph`'s typed state accumulating across nodes has no equivalent here. |
| 2 | Tool-call errors kill the entire agent run | 🟢 Closed | **Closed (2026-08-04), branch `fix/agent-tool-error-handling`**: `Agent.run()`'s tool loop (`agent.ts`) now wraps `tool.invoke()` in try/catch and feeds `{ error: <message> }` back to the model as that call's tool result — same pattern the existing "no such tool" case already used. The model gets a chance to retry, try another tool, or explain the failure, instead of the run throwing straight out. |
| 3 | No token-level streaming | 🟢 Closed | **Closed (2026-08-04), branch `feat/llm-token-streaming`**: `LLMProvider` gained an optional `chatStream(params, onText)`, implemented for real by both built-in providers (`client.messages.stream()` for Anthropic, `stream: true` chat completions for OpenAI, accumulating fragmented tool-call deltas by index). `Agent.run()`/`resume()`/`runAgent()` take an `onText` callback and use `chatStream` when both it and the callback are present, falling back to plain `chat()` otherwise — a custom `LLMProvider` without `chatStream` still works, just without incremental events. |
| 4 | No cross-run memory / checkpointing / durable execution | 🟡 Partial | **Closed for a single `Agent`** (2026-08-04, branch `feat/agent-checkpointing`): `Agent.run(input, {runId})`/`Agent.resume(runId)` + `CheckpointStore` seam (`packages/agents/src/checkpoint.ts`), backed by a real `createSemanticFsCheckpointStore()` that persists after every turn through `apps/filesystem`'s `write_context_file`/`read_context_file`/`tag_context_file` exports. A crash mid-loop no longer loses everything — `resume()` picks the loop back up from the last saved turn. **Still open**: `Crew.sequential`/`withManager`/`networked` don't checkpoint crew-level composition state (which sub-agent ran, in what order) — only individual `Agent`s constructed with a `checkpoint` store get durable progress. Also still open: this doesn't fix gap #2 — a checkpoint preserves the turns *before* a crash, not the crashing turn itself. |
| 5 | Zero observability/tracing | 🟡 Partial | **Closed for a single `Agent`'s turns/tool-calls (2026-08-04), branch `feat/agent-tracing`**: `StepTracer` seam (`packages/agents/src/tracing.ts`) + `AgentStepEvent` (`runId, agentName, turn, kind: "llm-turn"|"tool-call", toolName?, durationMs, error?`), emitted after every LLM turn and every tool call when both `trace` and `runId` are set — same "constructor-level seam, run-level activation" shape as checkpointing. `createContextBusStepTracer()` publishes to Context Bus topic `agent.step` for live tailing, via a new `apps/filesystem` export (`publish_context_event`) — the tool-export surface Context Bus didn't have before this, unlike Semantic FS. `createSemanticFsStepTracer()` writes to `/context/agent-traces/<runId>.json` for durable replay (`readAgentTrace()` reads it back), reusing checkpointing's exact resident-app-export pattern. `createAgentTracer()` (`trace: "full"`) does both. **Still open**: no token/cost accounting — no `LLMProvider` reports usage, so it's not in the event shape. No trace-ID correlation across a `Crew` — Agent-level only, same boundary checkpointing has. No list/browse-all-traces primitive — `readAgentTrace()` needs a known `runId`. |

## Tier 2 — credibility gaps once someone reads the code

| # | Gap | Status | Notes |
|---|-----|--------|-------|
| 6 | Multi-agent orchestration (the headline feature) has no unit tests and isn't in CI | 🟡 Partial | `Crew.withManager`/`Crew.networked` are still verified only by `crew-manager-milestone.mjs`/`crew-networked-milestone.mjs`, both requiring a live `ANTHROPIC_API_KEY` and explicitly excluded from `.github/workflows/agents-milestone.yml`. **Update (2026-08-04, gap #1's branch)**: `crew.test.ts` now exists (8 tests, no Docker/API key needed) — but for `parallel`/`loopUntil`/`route` only, using a fake `LLMProvider` the same way `agent.test.ts` does. `withManager`/`networked`/`sequential` are still untested outside the API-key-gated milestone scripts. |
| 7 | No LLM-call retry/backoff, no fallback models | 🟢 Closed | **Closed (2026-08-04), branch `feat/llm-retry-fallback`**: per-call retry already existed but was invisible/unconfigurable — `createAnthropicProvider()`/`createOpenAIProvider()` are thin adapters over `@anthropic-ai/sdk`/`openai`, and both SDK clients already retry 429/5xx/timeouts with their own backoff (`maxRetries: 2` default); both providers now expose `maxRetries` directly. The actual missing piece, a primary/secondary model chain, is new: `createFallbackProvider(providers, {onFallback?})` wraps an ordered `LLMProvider[]` into one — `chat()`/`chatStream()` try each in order, falling through to the next on any thrown error, propagating the last one's error unchanged if all fail. Works with any `LLMProvider` (built-in or custom); `Agent`/`createAgent` need no awareness of it — `llm` just accepts the wrapped provider like any other. |
| 8 | No human-in-the-loop at the agent-loop level | 🟢 Closed | **Closed (2026-08-04), branch `feat/agent-human-approval`**: `applyHumanApprovalGate(tools, options)` (`packages/agents/src/approval.ts`) generalizes `@berth/grants-server`'s existing request/approve/deny/webhook machinery from "container gets this filesystem capability" (async, takes effect on next boot) to "this agent gets to take its next action" (live, blocking). A gated tool call `POST /grants`s (`capability: "agent-action:<toolName>"`, tool input as `reason`), then polls `GET /grants/:id` until a human decides via `berth grants approve/deny` or `timeoutMs` (default 10min) elapses — fail-**closed**, the opposite of the governance gate's fail-open. Denied/timed-out both throw `HumanApprovalDeniedError`, caught generically by `Agent.run()`'s existing tool-error handling (gap #2) — no `Agent` loop changes needed. `only: string[]` scopes which tool names are gated (omit to gate everything). `createAgent({humanApproval})` wires it in without touching `Computer`. Doesn't touch `generate-capability-policy.ts`/Landlock — orthogonal, boot-time-only machinery, and there's no container to restart mid-`Agent.run()` anyway. |
| 9 | RAG/retrieval not surfaced to the agent framework | 🟡 Partial | **Closed for Semantic FS as a retriever (2026-08-04), branch `feat/agent-semantic-fs-retriever`**: `createSemanticFsRetriever()` (`packages/agents/src/retrieval.ts`) wraps Semantic FS's `query_context` + `read_context_file` exports into one `retrieve(text, {topK?})` call (query, then fetch content for each hit, dropping stale paths) and exposes it as a single `search_context` `Tool` via `asTool()`; `createAgent({retriever: "semantic-fs"})` wires it in automatically alongside the raw exports. **Still open**: no vector-DB integration (Pinecone/Weaviate/pgvector/etc.), no chunking for long documents, and no ingestion path beyond the existing `write_context_file`/`tag_context_file` exports — this makes querying ergonomic, it doesn't add a new way to get documents in. |
| 10 | No structured-output enforcement/repair loop | 🔴 Open | A Zod parse failure on tool input (server-side, inside the sandboxed app) becomes a thrown error (see #2) rather than being fed back to the model to retry with corrected arguments. No `.with_structured_output()` equivalent. |

## Tier 3 — ecosystem/breadth gaps, expected but worth naming

| # | Gap | Status | Notes |
|---|-----|--------|-------|
| 11 | ~6 first-party tool integrations vs. LangChain's hundreds | 🔴 Open | `apps/`: activity-feed, browser-native, code-editor, filesystem, github-assistant, hello-world-py, notes, terminal. No web search, no generic code-exec primitive, no Slack/Jira/DB connectors, no document loaders. | 13 | No eval harness for agent quality | 🔴 Open | `berth test` only checks manifest/export shape bijection — zero LLM invocation, zero behavioral assertion. No regression suite, no LLM-as-judge scaffolding. |

## Structural (architectural tradeoff, not a code fix)

| # | Gap | Status | Notes |
|---|-----|--------|-------|
| 14 | Docker/sandbox cold-start is a real adoption-friction cost | 🔴 Open (by design) | Every gap above assumes a booted sandbox container. Getting a "hello world" agent running requires Docker + the Landlock/context-bus/semantic-fs daemon stack, vs. `pip install langgraph` and a script. This is a genuine disadvantage for the framework-vs-framework comparison specifically — a tradeoff of the OS-first architecture, not something framework-code polish fixes. Worth being explicit about rather than silently absorbing into the other gaps. |

## Progress log

**2026-08-04 — Gap #9 (RAG/retrieval not surfaced to the agent framework), partially closed.** Branch `feat/agent-semantic-fs-retriever`, committed locally, not pushed.
- Confirmed `query_context` (`apps/filesystem`) only ever returns metadata (`path`/`task`/`relatedApps`/timestamps — `@berth/sdk`'s `SemanticFsQueryResult`), never a hit's content — calling it directly from an agent's tool list forces an N+1 round trip (one `query_context` call, then one `read_context_file` call per hit) before the model has anything to actually read.
- New `packages/agents/src/retrieval.ts`: `Retriever` interface (`retrieve`/`asTool`) + `createSemanticFsRetriever(computer)`, resolving `query_context`/`read_context_file` off `Computer.tools` the same suffix-match way checkpointing/tracing do (`findExportTool`, reused from `checkpoint.ts`), throwing immediately at construction if either is missing. `retrieve(text, {topK?})` (default `topK` 5) runs the query then fetches content for each hit concurrently via `Promise.all`, silently dropping any hit whose `read_context_file` call throws (a tagged path that's since been deleted/moved) rather than failing the whole call. `asTool(name?)` wraps it as one `Tool` (`"search_context"` by default) with a `{query, topK?} -> {documents}` shape a model can call directly.
- `createAgent({retriever: "semantic-fs" | Retriever})` (`agent.ts`) builds the retriever from the Computer and appends `.asTool()` to the tool list — additive, not a replacement: the raw `query_context`/`read_context_file` exports stay callable too.
- 7 new unit tests (`retrieval.test.ts`), following `checkpoint.test.ts`'s `fakeComputer`/`fakeTool` pattern (no Docker/API key needed): missing-tools throws, namespaced tool names resolve, `retrieve()` fetches content per hit, `topK` is respected, a stale hit's read failure doesn't fail the whole call, `asTool()` shape, custom tool name. All 66 tests in `packages/agents` pass; `tsc --noEmit` clean.
- Docs: `docs/agents-reference.md` gained a "Retrieval" section (between checkpointing and tracing, since all three build on the same Semantic FS export pattern), and `docs/semantic-fs-reference.md` gained a short cross-reference.
- Explicitly still open: no vector-DB integration (Pinecone/Weaviate/pgvector/etc.) — Semantic FS's own hybrid keyword+embedding index is the only backend; no chunking for long documents (retrieval returns whatever `read_context_file` reads back whole); no new ingestion path — getting a document *into* Semantic FS still means calling `write_context_file`/`tag_context_file` yourself, same as before this work.

**2026-08-04 — Gap #8 (no human-in-the-loop at the agent-loop level), closed.** Branch `feat/agent-human-approval`, committed locally, not pushed.
- Researched `packages/grants-server` first: it's a plain host-runnable Fastify + `node:sqlite` service (not Docker/container-specific itself), reachable identically from the host or from inside a sandbox — unlike Context Bus (gap #5), no new resident-app export was needed to reach it from an `Agent`. Its *existing* consumer, `requestCapability()`/`generate-capability-policy.ts`, is fire-and-forget-then-boot-time-merge, structurally incompatible with gating a live call (nothing polls or blocks for a decision, and Landlock rulesets can't be widened on an already-running process anyway) — so that consumption path wasn't reusable, only the server + REST contract underneath it was.
- New `packages/agents/src/approval.ts`: `applyHumanApprovalGate(tools, {grantsServerUrl, requesterName, only?, pollIntervalMs?, timeoutMs?})` — modeled structurally on `governance.ts`'s "wraps a tool list" shape (simpler here, since there's no Computer/manifest plumbing to resolve a resident governor app through). A gated call `POST /grants`s (`capability: "agent-action:<toolName>"`, JSON-stringified input as `reason`), then polls `GET /grants/:id` until `approved`/`denied` or `timeoutMs` (default 10min, fail-**closed** — deliberately the opposite of governance.ts's fail-open, since a human gate that silently passed through on timeout wouldn't be one). Both denial and timeout throw `HumanApprovalDeniedError`, which `Agent.run()`'s existing generic tool-error handling (gap #2) already catches and feeds back to the model as `{error}` — zero changes to `agent.ts`'s loop itself.
- `createAgent({humanApproval})` wires it in: wraps `computer.tools` before constructing the `Agent`, `requesterName` defaulting to the Agent's own `name`.
- `@berth/grants-server` added as a real dependency of `@berth/agents` (for the `GrantRecord` type only — no client library existed to reuse, so `approval.ts` talks to the REST API directly via `fetch`).
- 5 new unit tests (`approval.test.ts`), each spinning up a *real* `createGrantsServer()` instance on an ephemeral port (temp SQLite dir, torn down after) rather than mocking grants-server's own logic — matching this package's existing "real, not mocked" posture for infra it can run without Docker (`fleet-computer.test.ts`'s fake-adapter-backed-by-a-real-HTTP-server is the same idea). Covers: approve unblocks the real underlying `tool.invoke()`; deny throws with the human's reason; an undecided grant times out; `only` leaves other tools ungated (and creates no grant for them); the exact capability/reason shape a human reviewer would see. All 59 tests in `packages/agents` pass; `tsc --noEmit` clean.
- Docs: `docs/agents-reference.md` gained a "Human-in-the-loop" section (between governance and `Agent`/`Crew`), and `docs/capability-tokens-reference.md`'s grants-server section gained a short cross-reference to this second, structurally different consumer.
- Explicitly still open: this gates *tool calls*, not the LLM's own text/turn — there's no way to pause and ask a human "should the agent even keep going" independent of a specific tool call being made. No UI beyond the existing `berth grants` CLI/REST API — a human still needs to know to go look.

**2026-08-04 — Gap #7 (no LLM-call retry/backoff, no fallback models), closed.** Branch `feat/llm-retry-fallback`, committed locally, not pushed.
- Turned out per-call retry/backoff already existed, just invisible: `@anthropic-ai/sdk` and `openai`'s Node clients both default `maxRetries: 2` with their own exponential backoff on retriable errors, and neither `createAnthropicProvider()` nor `createOpenAIProvider()` exposed a way to see or change that. Both gained a `maxRetries?: number` option, passed straight through to the underlying client constructor.
- New `packages/agents/src/providers/fallback.ts`: `createFallbackProvider(providers: LLMProvider[], {onFallback?})` — tries `providers[0]`, falls through to `providers[1]`, etc. on any thrown error (i.e. once that provider's own SDK-level retries are exhausted), propagating the last provider's error unchanged if every one fails. `onFallback(error, failedProvider, nextProvider)` fires once per fallback, for logging — it's not a retriable-vs-not classifier, every error falls through. `chatStream` is present on the wrapped provider only when every provider in the chain implements it, matching `Agent.run()`'s existing "absent chatStream means no incremental events" contract.
- Genuinely new capability (unlike the `maxRetries` half): nothing previously let a run survive a whole provider being down, only a single flaky call.
- 9 new unit tests (`fallback.test.ts`) with fake `LLMProvider`s, no Docker/API key needed. **Caught and fixed a real test-infra bug in the process**: this package's `test` script is `node --test dist/**/*.test.js`, and under POSIX `sh` (what `npm`/`turbo` actually invoke scripts with, not the interactive zsh shell) `**` doesn't glob-expand recursively the way it does in zsh — it only matches exactly one directory level. A test file nested one level deeper than the rest (first written at `providers/fallback.test.ts`) made the shell's glob switch from "no match, pass the literal pattern through to Node's own (correctly recursive) glob handling" to "partially match, expand to just the nested file, silently dropping every flat-level test file from the run" — 54 tests silently became 9, with no error. Moved the test file back to flat (`src/fallback.test.ts`), matching every other test file in this package, and confirmed via the literal `npm test` entry point (not just `node --test` with an explicit file list) that all 54 tests run. Documented here since another nested test file anywhere in this package's `src/` would silently reintroduce the same breakage.
- Docs: `docs/agents-reference.md` gained a "Retries and a fallback model chain" subsection.
- No changes needed to `Agent`/`createAgent`/`Crew` — `createFallbackProvider()`'s output is just another `LLMProvider`, accepted by `llm` exactly like `createAnthropicProvider()`/`createOpenAIProvider()`/a custom implementation.
- Explicitly still open: falling back mid-`chatStream()` isn't clean — `onText` may already have fired with the failed provider's partial text before the switch, and the next provider's stream restarts from nothing rather than continuing seamlessly.

**2026-08-04 — Gap #1 (no state-graph/node-edge orchestration model), partially closed.** Branch `feat/crew-composable-functions`, committed locally, not pushed.
- `Crew.parallel(agents, {merge?})` (`crew.ts`): runs every agent against the same input via `Promise.all`, then combines with `merge` (defaulting to a `## <name>` heading join) — the fan-out-then-merge shape none of the original three could express.
- `Crew.loopUntil({agent, until, maxIterations?})`: repeatedly runs one agent, piping its own output back in as the next input, checking `until(result, iteration)` after each run; stops on the first `true` or after `maxIterations` (default 10) — the cycle.

- 8 new unit tests (`crew.test.ts`, the first tests `Crew` has ever had — see gap #6) covering default/custom merge, loop-until-satisfied, loop-hits-maxIterations, route-dispatches, route-falls-back, route-throws-naming-the-answer. All 34 tests in `packages/agents` pass; `tsc --noEmit` (the package's lint) is clean.
- Docs: `docs/agents-reference.md` gained a "Composable `Crew` functions" subsection under "Agent and Crew".
- Explicitly still open: no explicit shared-state object threaded across steps — every function here only ever passes a `string`, so a LangGraph `StateGraph`'s typed accumulating state has no equivalent yet. Crew-level composition state still isn't checkpointed (same boundary gap #4 already called out for the original three).

**2026-08-04 — Gap #3 (no token-level streaming), closed.** Branch `feat/llm-token-streaming`, committed locally, not pushed.
- `LLMProvider.chatStream?(params, onText)` (`types.ts`): same request/response shape as `chat()`, but calls `onText(delta)` per chunk of assistant text before resolving with the same `LLMTurn`.
- `createAnthropicProvider()` implements it with `client.messages.stream()` + `.on("text", ...)`, resolving via `.finalMessage()`. `createOpenAIProvider()` implements it with `stream: true` chat completions, accumulating `delta.tool_calls[].index`-keyed fragments (id/name/arguments each arrive split across chunks) into complete tool calls once the stream ends.
- `Agent.run(input, {onText})` / `Agent.resume(runId, {onText})` / `runAgent({onText})`: the tool-use loop calls `chatStream` instead of `chat` only when both `onText` and `llm.chatStream` are present, per turn. No `onText`, or a provider without `chatStream` (any custom `LLMProvider`) → identical behavior to before, silently.
- 4 new unit tests in `agent.test.ts` using a fake provider with a scripted `chatStream`, covering: deltas arrive and the final text still matches; `chatStream` is never called without `onText`; `onText` without `chatStream` degrades to `chat()` instead of throwing; `resume()` streams the remaining turns after a checkpointed crash.
- Docs: `docs/agents-reference.md`'s "bring-your-own-LLM seam" section gained the `chatStream` signature and an example.
- Explicitly still open: streaming is per-turn text only — tool-call arguments aren't streamed (only assembled complete at turn end), and this doesn't touch `Crew`'s composition layer, same scope boundary as the checkpointing work.

**2026-08-04 — Gap #2 (tool-call errors kill the run), closed.** Branch `fix/agent-tool-error-handling`.

- New test in `agent.test.ts`: a throwing tool doesn't end the run, the model gets a second turn and can recover.
- Docs: `docs/agents-reference.md` gained a short note under "Agent and Crew", and the checkpointing section's "doesn't fix" callout for this gap was removed since it's now fixed.
- Explicitly still open: a hard process crash *during* `tool.invoke()` (not a thrown JS error) still loses that turn — only the checkpoint from before it started is recoverable.
