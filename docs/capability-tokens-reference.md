# Capability Tokens Reference (Phase 3)

Phase 3 is the PRD's one kernel-level bet: turning `berth.yml`'s declared `capabilities:` into something the kernel actually enforces, not something an SDK politely checks before making a call on the agent's behalf.

## What's implemented

**`agent-init`** (`packages/agent-init`, Rust) sits between `entrypoint.sh` and whatever command it hands off to (the SDK runtime, `check-exports.js`, `npm test`, ...). It:

1. Reads a capability policy JSON (generated by `@berth/sdk`'s `generate-capability-policy.ts` from `berth.yml`, so the YAML/capability-glob parsing logic stays in one place — `@berth/manifest-schema` — instead of being reimplemented in Rust).
2. Builds a [Landlock](https://landlock.io/) ruleset restricting **write-ish filesystem access** (write, create, delete, rename — not execute) to only the paths declared via `filesystem:write:<path>` capabilities, plus a baseline of `/tmp`. **Read-path and network scoping are also enforced, opt-in** — see below.
3. Calls `landlock_restrict_self()` on itself.
4. `exec()`s into the original command.

Landlock restrictions are inherited across `execve()` and can never be lifted — once applied, the resident app's runtime *and every process it spawns* are bound by them, enforced by the kernel at the syscall boundary. This is the PRD's actual differentiating claim: a compromised or misbehaving resident app can't write outside its granted paths because the kernel refuses the syscall, not because some SDK code declined to make the call.

**`requestCapability()`** (`@berth/sdk`) checks whether a requested capability matches something declared in `berth.yml` (via `@berth/manifest-schema`'s `matchesCapability()`) and reports `{ granted, token, issuedAt, expiresAt }` honestly — it doesn't *decide* anything the kernel hasn't already decided at process boot. The token is a real HMAC-SHA256 signature (keyed by `BERTH_TOKEN_SECRET`, generated once per container boot in `entrypoint.sh`) over `appName:capability:issuedAt:expiresAt`, with a 5-minute expiry — `verifyCapabilityToken()` recomputes and checks it. See "What's deliberately deferred" below for what this doesn't cover yet.

## Read and network scoping — opt-in, not on by default

Write-path restriction is always active. Read-path and network scoping are **opt-in**: `generate-capability-policy.ts` only turns them on when the manifest declares at least one `filesystem:read:<path>` or `network:connect:<port>` capability — an app that declares neither keeps today's fully-open read/network behavior, unchanged.

- **Reads**: enumerating every path Node/Alpine need to read just to function is still fragile — that reasoning hasn't gone away. So when read scoping *is* enabled (because the app declared a read path), the effective allow-list is a fixed baseline (`/usr`, `/lib`, `/etc`, `/proc`, `/dev`, `/tmp`, the app's own working directory) **plus** whatever the app declared — narrowing visibility to baseline-plus-declared, never below what the runtime itself needs. `apps/filesystem/berth.yml` already declares `filesystem:read:/workspace` and `filesystem:read:/context`, so this is exercised by the existing `apps/filesystem` app, not just a hypothetical one — see `capability-enforcement.mjs`'s Test 3/4.
- **Network**: Landlock's network scoping (ABI v4 / kernel 6.7+, already in the vendored `landlock` crate — no upgrade needed) restricts by **port** via a new `network:connect:<port>` capability convention, not by domain — it still can't express something like `browser:navigate:*.github.com`. Real domain-scoped filtering needs either a local proxy with SNI/Host inspection or an eBPF `cgroup/connect` hook with runtime DNS-resolution matching — both meaningfully bigger scope than this pass, and still not attempted. Non-filesystem, non-network capabilities (`browser:*`, `github:*`, ...) are still just recorded in the policy and reported by `requestCapability()`, not kernel-enforced.

## What's deliberately deferred (by explicit decision, not oversight)

- **Human admin approval flow.** The PRD's "human admins approve grants; agents never see raw secrets" describes an async approval workflow (a queue, a UI, someone clicking approve). Being built as a separate piece of work (`packages/grants-server`) — see that package's own docs once it lands. `generate-capability-policy.ts` already has the hook to consult it (`BERTH_GRANTS_SERVER_URL`), inert until that server exists.
- **Domain-scoped network filtering.** Port-based scoping is real; domain/SNI-based filtering is not, as above.
- **Per-syscall-denial audit logging.** `agent-init` logs the *policy it applied* at boot as a structured JSON line (`{"event":"capability_policy_applied",...}`, visible in container logs) — that's a real audit record of what was granted, but not a live stream of every individual denied syscall. Real per-event audit logging needs either the Linux audit subsystem (`auditd`, needs privileges typically unavailable in an unprivileged container) or privileged eBPF LSM hooks — both out of scope here, permanently, not just for this pass, since Landlock itself has no deny-notification hook to build on.

## Verification status — read this before trusting Phase 3 in any environment

**Verified:** the full pipeline runs correctly end-to-end via real Docker builds and containers (not just compiled) — `agent-init` builds inside Alpine, the capability policy JSON is generated correctly from `berth.yml`, `agent-init` runs and hands off to the runtime without breaking it (Node still starts, RPC still works, `berth test`/`berth dev` still pass), and `requestCapability()` correctly grants/denies based on declared capabilities (unit-tested).

**NOT verified on this dev machine — a real environment limitation, not a code defect:** actual kernel-level denial of a write (or, as of this pass, a read) outside a declared path. `packages/docker-orchestrator/test/capability-enforcement.mjs` proves both (write/read inside the declared+baseline paths succeed; path-traversal write/read outside them gets refused with `EACCES`/`EPERM`) — but on Docker Desktop for Mac, the linuxkit VM's kernel (confirmed via `cat /sys/kernel/security/lsm` inside a privileged container, after `mount -t securityfs securityfs /sys/kernel/security`) reports only `capability,bpf` as active LSMs. **Landlock is not in the active LSM stack on this specific dev environment**, even though the syscalls exist — `landlock_restrict_self()` returns `ruleset=NotEnforced`, which the `landlock` crate treats as a graceful no-op (by design, so older kernels don't crash), not an error. This was confirmed to not be a seccomp issue either (`--security-opt seccomp=unconfined` made no difference). Confirmed by hand on this dev machine: `agent-init` still parses `readPaths`/`networkPorts` and logs the structured audit line correctly (both with and without those fields present, for backward compatibility with policy files written before this pass) even when the ruleset itself can't be enforced here.

This is expected to work correctly on:
- Most bare-metal Linux hosts (Landlock has been mainline since kernel 5.13, generally enabled by distros)
- GitHub Actions `ubuntu-latest` runners
- Real cloud VMs running modern Linux

**Before treating Phase 3 as passing any real security review, re-run `capability-enforcement.mjs` on one of those and confirm it logs `ruleset=FullyEnforced` (or `PartiallyEnforced`) and hard-asserts the traversal write is denied** — the script already detects which case it's in and only treats the denial as a required assertion when Landlock is actually active; on this dev machine it correctly reports "NOT VERIFIED (expected in this environment)" instead of a false pass or a false failure.

### CI closes this gap

`.github/workflows/capability-enforcement.yml` runs this exact script on GitHub Actions `ubuntu-latest` on every push to `main`, every PR, and on demand via `workflow_dispatch`. Because that runner is a real Linux kernel (not Docker Desktop's linuxkit VM), `capability-enforcement.mjs` is expected to detect `ruleset=FullyEnforced` there and hard-assert the traversal write is denied. The script additionally treats a `NotEnforced` result as a hard CI failure (not just a warning) when `process.env.CI` is set — since Landlock going inactive on `ubuntu-latest` would itself be a real regression worth catching, not an expected environment limitation like on this Mac.

This closes the verification gap going forward: once this workflow has run green at least once on a real push, Phase 3's kernel enforcement claim is confirmed, and any future regression in `agent-init`'s Landlock ruleset construction gets caught by CI rather than silently reintroduced.
