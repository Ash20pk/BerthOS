# Capability Enforcement Reference (Phase 3)

> **The filename is a fossil.** Capability *tokens* were removed in [REMEDIATION.md 1.10](./internal/REMEDIATION.md#110--capability-tokens-are-never-verified-anywhere) — nothing verified them, and the signing secret lived in the environment of the app they were meant to constrain. The file keeps its name only because 20-odd docs and source comments link to it; the subject was always kernel enforcement plus the grants flow, both of which are real.

Phase 3 is the one kernel-level bet here: turning `berth.yml`'s declared `capabilities:` into something the kernel actually enforces, not something an SDK politely checks before making a call on the agent's behalf.

## What's implemented

**`agent-init`** (`packages/agent-init`, Rust) sits between `entrypoint.sh` and whatever command it hands off to (the SDK runtime, `check-exports.js`, `npm test`, ...). It:

1. Reads a capability policy JSON (generated by `@berth/sdk`'s `generate-capability-policy.ts` from `berth.yml`, so the YAML/capability-glob parsing logic stays in one place — `@berth/manifest-schema` — instead of being reimplemented in Rust).
2. Builds a [Landlock](https://landlock.io/) ruleset restricting **write-ish filesystem access** (write, create, delete, rename, truncate — not execute) to only the paths declared via `filesystem:write:<path>` capabilities, plus a baseline of `/tmp`. **Read-path scoping is also enforced, opt-in; network scoping is enforced deny-by-default** — see below.
3. Calls `landlock_restrict_self()` on itself.
4. Drops `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, and `CAP_NET_RAW` — via `drop_all_capabilities()`, from its own (and thus the resident app's, post-`exec()`) bounding, inheritable, and ambient capability sets. The first two are the only capabilities this repo's container config ever adds beyond Docker's own defaults (`SYS_ADMIN` for semantic-fs's FUSE mount, `NET_ADMIN` for mesh-daemon's wg0) — since every container here runs every process as root with no `USER` directive, leaving them in place would hand the resident app the same elevated capabilities as the daemons they were actually meant for. `CAP_NET_RAW` is different: nothing adds it, because Docker grants it *by default*, and it is what lets a process open `AF_PACKET` sockets and speak TCP/IP from userspace without ever calling the `connect(2)` that Landlock's `AccessNet::ConnectTcp` rule watches for — i.e. it is a bypass of the network scoping described below, not merely extra privilege. Dropping it also means `ping` no longer works inside a sandbox, which is worth knowing before debugging one. This is deliberately *not* a full `caps::clear`: dropping the entire capability set was found (on a kernel where Landlock is actually enforced) to also strip `CAP_DAC_OVERRIDE`, which root relies on to write into a bind-mounted directory it doesn't own (e.g. this repo's own CI checkout) — every write under a declared write path started failing with `EACCES`. Runs regardless of whether the Landlock ruleset above was applied successfully, and logs its own audit event (`capabilities_dropped`) separate from the per-boot `capability_policy_applied` line. A dropped bounding set is only a ceiling *within the process's own user namespace*, which is why step 5 below exists — without it, `unshare(CLONE_NEWUSER)` hands the app a fresh `CAP_FULL_SET` and the drop means nothing. This is boot-time hardening for Linux capabilities specifically — an orthogonal kernel mechanism from Landlock's filesystem/network-port scoping, closing off `CAP_SYS_ADMIN`/`CAP_NET_ADMIN` misuse even where Landlock itself has nothing to say.
5. Installs a **seccomp-bpf filter refusing namespace creation** — for every app, unconditionally (`packages/agent-init/src/seccomp.rs`). `unshare(2)` and `clone(2)` are refused with `EPERM` when any `CLONE_NEW*` flag is set, `setns(2)` is refused outright, and `clone3(2)` returns `ENOSYS` because seccomp cannot dereference the pointer its flags arrive behind (the same answer Docker's own default profile gives, so libc falls back to `clone(2)` rather than failing). This is what makes step 4's capability drop mean anything: creating a user namespace requires no privilege at all, and the kernel grants its creator a full capability set — including a fresh `CAP_FULL_SET` bounding set — inside the new namespace. `unshare -Urm` was enough to get `mount(2)` back. Docker's default seccomp profile blocks this for containers generally, but stops doing so when the container holds `CAP_SYS_ADMIN`, which every Berth container does for semantic-fs's FUSE mount. Landlock's filesystem rules were never affected (they are inode-based and survive namespace tricks); what came back was every `CAP_SYS_ADMIN`-gated syscall Landlock does not cover. Still open: the grant itself is container-wide, and the daemons that start before `agent-init` carry it with no filter.
6. Installs a **seccomp-bpf filter refusing UDP and raw sockets**, but only for an app that declared no network capability at all (`packages/agent-init/src/seccomp.rs`). Landlock's network rights cover TCP connect and bind and nothing else — no ABI, present or announced, has a UDP, ICMP, or raw-socket right — so "declared no network capability" previously still meant unrestricted UDP: DNS-tunnelled exfiltration, QUIC, arbitrary C2. The filter denies `socket(AF_INET|AF_INET6, SOCK_DGRAM|SOCK_RAW)` and all of `AF_PACKET` with `EPERM`, and like the Landlock domain it survives `execve()` and can't be lifted. It is deliberately not installed for an app that declared even one port, because such an app needs DNS (UDP 53) for that port to be reachable by name and Landlock's per-port model can't express "UDP 53 only" — routing those apps' DNS through the egress broker is the open follow-up. `AF_UNIX` (all local RPC) and `AF_NETLINK` are untouched.
7. `exec()`s into the original command.

Landlock restrictions are inherited across `execve()` and can never be lifted — once applied, the resident app's runtime *and every process it spawns* are bound by them, enforced by the kernel at the syscall boundary. This is the actual differentiating claim here: a compromised or misbehaving resident app can't write outside its granted paths because the kernel refuses the syscall, not because some SDK code declined to make the call.

**`requestCapability()`** (`@berth/sdk`) checks whether a requested capability matches something declared in `berth.yml` (via `@berth/manifest-schema`'s `matchesCapability()`) and reports `{ granted }`, plus `pending` when the denial was submitted to a grants server for human approval. It reports the decision the kernel already made at boot; it does not grant anything itself, and it no longer returns a token (1.10).

## Read scoping (opt-in) and network scoping (deny-by-default)

Write-path restriction is always active.

- **Reads** are **opt-in**: `generate-capability-policy.ts` only turns on read scoping when the manifest declares at least one `filesystem:read:<path>` capability — an app that declares none keeps today's fully-open read behavior, unchanged. Enumerating every path Node/Alpine need to read just to function is still fragile — that reasoning hasn't gone away. So when read scoping *is* enabled, the effective allow-list is a fixed baseline (`/usr`, `/lib`, `/etc`, `/proc`, `/dev`, `/tmp`, the app's own working directory) **plus** whatever the app declared — narrowing visibility to baseline-plus-declared, never below what the runtime itself needs. `apps/filesystem/berth.yml` already declares `filesystem:read:/workspace` and `filesystem:read:/context`, so this is exercised by the existing `apps/filesystem` app, not just a hypothetical one — see `capability-enforcement.mjs`'s Test 3/4.
- **Declared filesystem paths are confined to `/workspace`, `/context`, `/tmp`, and `/app`.** This is validated at manifest-load time (`@berth/manifest-schema`'s `ALLOWED_FILESYSTEM_SCOPE_PREFIXES`) and again in `agent-init` for write paths, which duplicates the list deliberately because it's the process running the `create_dir_all()`. The reason is that half of the pipeline: a declared write path is created as uid 0 with `CAP_SYS_ADMIN` *before* the ruleset is applied, so an unconstrained scope let a `berth.yml` from a registry or a PR name any path in the container and have it both created and granted. It used to land on the developer's own host too, through `berth dev`'s workspace bind mount; that mount is read-only since [1.6](./internal/REMEDIATION.md#16--berth-dev-bind-mounts-the-whole-host-repo-read-write), so a path that doesn't already exist now fails with `EROFS` and has its grant skipped, exactly like a missing read path. `filesystem:write:/` is rejected (it grants the whole container filesystem), as is a non-canonical path or a `*` anywhere other than a trailing `/*` — `filesystem:write:*` used to create and grant a directory literally named `*`. **Declared read paths are no longer created at all**, since a read grant needs no directory to exist for the app to work: a missing one is reported as a loud warning naming the consequence (the grant is skipped permanently, because the ruleset is sealed moments later). In a multi-app container that means an app declaring `filesystem:read:` on a sibling's directory can lose the grant if it boots first — `entrypoint.sh` starts every app's chain concurrently with no ordering barrier. Fixing that needs boot ordering, not a root mkdir of arbitrary manifest paths.
- **Network** is **deny-by-default**: an app that declares no `network:connect:<port>` capability gets a Landlock ruleset that allows zero outbound TCP connections, plus the seccomp filter above closing the UDP and raw-socket paths Landlock can't see — not "whatever the container's network namespace happens to allow" as before this pass. Landlock's network scoping (ABI v4 / kernel 6.7+, already in the vendored `landlock` crate) restricts by **port**, not by domain, so an app that needs to reach arbitrary hosts would declare `network:connect:*` — an explicit, audited escape hatch that skips building a per-port ruleset entirely, rather than enumerating all 65535 ports. No first-party app actually does this: `browser-native`, which navigates to whatever URL the agent gives it, instead scopes to just `network:connect:8090` (the egress broker's loopback port) and lets the broker enforce `browser:navigate:<pattern>` host-matching at the application layer — see [egress broker reference](./egress-broker-reference.md). This is deliberately coarser than domain-scoped filtering (it can't express something like "only `*.github.com`") — see "What's still deliberately deferred" below. Non-filesystem, non-network capabilities (`browser:*`, `github:*`, ...) are still just recorded in the policy and reported by `requestCapability()`, not kernel-enforced on their own.
- **Binding a port to listen on is a *separate* grant from connecting out on one.** `AccessNet::from_all` (what `restrict_network` handles) denies-by-default both `AccessNet::ConnectTcp` *and* `AccessNet::BindTcp` the moment network scoping is active at all — `network:connect:<port>` capabilities only ever grant the former. `generate-capability-policy.ts`'s `bindPorts` field (populated from `BERTH_HTTP_RPC_PORT`/`BERTH_HTTP_RPC_APP`, the env vars `@berth/sdk`'s HTTP RPC bridge reads — see [`docs/agents-reference.md`](./agents-reference.md#reaching-a-computer-from-outside-nodedocker---http-rpc)) is the one thing today that needs this: an app whose own process is going to `listen()` on a port, not just connect out on one. This isn't a `berth.yml`-declarable capability — it's an orchestration-level fact about which single app in a container is hosting the bridge, computed the same way `runtime.ts` itself decides which app binds it.

## Human admin approval — `@berth/grants-server`

The principle that human admins approve grants and agents never see raw secrets is now real, with one architectural wrinkle worth understanding before relying on it: **Landlock rulesets are fixed at `agent-init`'s `restrict_self()` call and can never be widened afterward** — only narrowed, by the kernel API's own design. So an approved grant can never be added to an *already-running* process. Approval takes effect on the app's **next container restart**, when `generate-capability-policy.ts` re-runs and picks up the newly-approved grant — not live, and not instantaneous.

- **`packages/grants-server`** is a standalone Fastify + `node:sqlite` service (`berth-grants` binary, mirrors `packages/registry-server`'s pattern exactly) storing `grants(id, appName, capability, status, reason, requestedAt, decidedAt, decidedBy)`. `POST /grants` creates a pending request (open — any app that can reach the server can ask); `GET /grants?status=&app=` lists (open). An optional `BERTH_GRANTS_WEBHOOK_URL` fires a best-effort POST on every new pending grant (wire it to Slack/Discord/whatever — this repo doesn't own notification infra beyond that one webhook call).
- **`POST /grants/:id/approve|deny` require a bearer operator token.** Without this, the sandboxed app whose request is pending could reach the same `host.docker.internal` path `requestCapability()` uses and approve its own escalation — a real defeat of the "human admin approves" story, not a hypothetical. `createGrantsServer({ operatorToken })` accepts one explicitly; omit it and one is minted on first boot and persisted at `<dataDir>/operator.token` (mode `0600`) so it survives a restart. The `berth-grants` binary reads `BERTH_GRANTS_OPERATOR_TOKEN` first, falling back to that persisted file, and prints the token once at startup when it wasn't passed via the env var. Sandboxed apps never receive this token — only whoever runs `berth grants approve/deny` does.
- **`requestCapability()`** (`@berth/sdk`): when a requested capability isn't statically declared *and* `BERTH_GRANTS_SERVER_URL` is set (threaded in via `--grants-server=<url>` on `berth dev`/`test`/`deploy`), it submits a pending grant request (best-effort, never blocks the caller if the server's unreachable) and returns `{ granted: false, pending: true }` instead of a bare denial. This path never needs the operator token — requesting is intentionally open.
- **`generate-capability-policy.ts`**: when `BERTH_GRANTS_SERVER_URL` is set, fetches `GET /grants?status=approved&app=<name>` and merges the results into `writePaths`/`readPaths`/`networkPorts` alongside `berth.yml`'s statically-declared capabilities, before writing the policy file `agent-init` reads at boot.
- **CLI**: `berth grants list|approve|deny` (`packages/cli/src/commands/grants/`), talking to the server's REST API via `--server` (default `http://127.0.0.1:4874`). `approve`/`deny` take `--token` (or `BERTH_GRANTS_TOKEN`) — the operator token printed by `berth-grants` at startup, or read from `<dataDir>/operator.token`.
- **Omitted by default**: no `--grants-server` flag means `BERTH_GRANTS_SERVER_URL` is never set, which is a no-op everywhere above — today's fully-static, no-async-workflow behavior is unchanged unless you opt in.

Verified for real, not just unit-tested: `packages/docker-orchestrator/test/grants-server-milestone.mjs` runs a full pending → `berth grants approve`-equivalent HTTP round trip against a real running `berth-grants` server (including a real, asserted 401 when the app that requested the grant tries to approve it without the operator token), boots a real container with `BERTH_GRANTS_SERVER_URL` set, and asserts the approved `network:connect:<port>` capability (one `apps/filesystem/berth.yml` does not statically declare) lands in the freshly-written `capability-policy.json`'s `networkPorts`. Wired into CI via `.github/workflows/grants-server-milestone.yml`.

`@berth/agents`'s `applyHumanApprovalGate()` (`packages/agents/src/approval.ts`) is a second, structurally different consumer of the same `berth-grants` server — a live, blocking gate on an `Agent`'s tool calls, not a boot-time capability merge. It never touches `generate-capability-policy.ts`/Landlock, since there's no container to restart mid-`Agent.run()` to pick up a decision the way `requestCapability()`'s async path does — see [`docs/agents-reference.md`](./agents-reference.md#human-in-the-loop-gating-a-live-tool-call-on-a-human-decision).

## What's still deliberately deferred (by explicit decision, not oversight)

- **Domain-scoped network filtering at the kernel level.** Landlock's own port-based scoping is real; domain/SNI-based filtering isn't possible at that layer, as above. A host-level egress broker now covers this for `browser:navigate:*` specifically — see `docs/egress-broker-reference.md`. Path/verb-level API scoping (`github:read:repos` vs `github:write:issues`) is now covered too, via a real TLS-terminating MITM broker — see `docs/github-api-scoping-reference.md`.
- **Per-syscall-denial audit logging.** `agent-init` logs the *policy it applied* at boot as a structured JSON line (`{"source":"agent-init","event":"capability_policy_applied",...}`, visible in container logs, and parseable as-is — these lines deliberately carry no `[agent-init]` prefix, unlike the human-readable ones around them) — that's a real audit record of what was granted, but not a live stream of every individual denied syscall. Real per-event audit logging needs either the Linux audit subsystem (`auditd`, needs privileges typically unavailable in an unprivileged container) or privileged eBPF LSM hooks — both out of scope here, permanently, not just for this pass, since Landlock itself has no deny-notification hook to build on.

## Verification status — read this before trusting Phase 3 in any environment

**Verified:** the full pipeline runs correctly end-to-end via real Docker builds and containers (not just compiled) — `agent-init` builds inside Alpine, the capability policy JSON is generated correctly from `berth.yml`, `agent-init` runs and hands off to the runtime without breaking it (Node still starts, RPC still works, `berth test`/`berth dev` still pass), and `requestCapability()` correctly grants/denies based on declared capabilities (unit-tested).

**Regression found and fixed (2026-08-05):** the "capability policy JSON is generated correctly" claim above was true when written, then silently stopped being true — `generate-capability-policy.ts`'s `main()` was gated behind `if (import.meta.url === \`file://${process.argv[1]}\`)`, meant to detect "was this run directly, not imported by a test." Every real invocation goes through the `node_modules/@berth/sdk` pnpm symlink every resident app has, and Node's ESM loader resolves `import.meta.url` *through* that symlink to the package's real location while leaving `process.argv[1]` as the as-invoked (symlinked) path — the two never matched, so `main()` silently never ran on any real container boot, no error, exit 0. **Practical effect while this was broken: no capability policy file was ever written, so `agent-init` always took its documented fail-open "no policy file" path and ran every app fully unrestricted — Landlock enforcement was a complete no-op repo-wide, independent of whether the host kernel could enforce Landlock at all.** Confirmed by hand inside a real container (`import.meta.url` resolved to `.../packages/sdk/dist/...`, `process.argv[1]` stayed `.../apps/browser-native/node_modules/@berth/sdk/dist/...`) before fixing it by `realpathSync()`-resolving `process.argv[1]` before the comparison. A real, Docker-free regression test (`generate-capability-policy.test.ts`, spawns the compiled script through an actual symlink, mirroring the pnpm layout) now covers this specific failure mode — confirmed it fails against the pre-fix code and passes against the fix. This was caught incidentally while verifying an unrelated feature (generalizing the egress broker's `network:host:*` capability to non-browser apps), not by any existing test noticing on its own — every test exercising the "unenforced" path (e.g. Test 8 below) treats "policy file missing" and "kernel lacks Landlock" as the same accepted failure mode on this dev machine, so a missing file was indistinguishable from this Mac's already-expected Landlock limitation until inspected directly.

**A second regression found and fixed (2026-08-05, same day, unrelated feature):** adding a local HTTP RPC bridge (`startContainer()`'s `httpRpc` option, `Computer.boot({httpRpc})`, `berth os up --http-rpc` — see [`docs/agents-reference.md`](./agents-reference.md#reaching-a-computer-from-outside-nodedocker---http-rpc)) passed every local test on this dev machine, then failed in CI with the resident app's own `listen()` call refused — `ECONNREFUSED` from the host side for the entire retry window, never once succeeding. Root cause: `restrict_network`'s `AccessNet::from_all` denies **both** `AccessNet::ConnectTcp` and `AccessNet::BindTcp` by default the moment network scoping is active at all, but the only grant this file ever built was `NetPort::new(port, AccessNet::ConnectTcp)` from `network_ports` — nothing anywhere granted `BindTcp` for any port, ever. Invisible on this dev machine because Landlock is `NotEnforced` here regardless (fail-open, see below) — the `listen()` call succeeds unconditionally whether or not the (never-built) bind grant would have allowed it. On GitHub Actions' real kernel, the ruleset actually enforces, and the app's own `bind()`/`listen()` syscall got kernel-level `EPERM` the whole time. Fixed by adding a separate `bindPorts` field (`generate-capability-policy.ts`'s `computeBindPorts()`, populated from `BERTH_HTTP_RPC_PORT`/`BERTH_HTTP_RPC_APP` — an orchestration-level fact, not a `berth.yml`-declarable capability) and a corresponding `NetPort::new(port, AccessNet::BindTcp)` grant in `agent-init`. Caught by CI catching a genuine kernel-enforcement difference this dev machine structurally cannot — exactly the gap "CI closes this gap" below exists to cover, just for a brand-new feature rather than a pre-existing one.

**NOT verified on this dev machine — a real environment limitation, not a code defect:** actual kernel-level denial of a write (or, as of this pass, a read) outside a declared path. `packages/docker-orchestrator/test/capability-enforcement.mjs` proves both (write/read inside the declared+baseline paths succeed; path-traversal write/read outside them gets refused with `EACCES`/`EPERM`) — but on Docker Desktop for Mac, the linuxkit VM's kernel (confirmed via `cat /sys/kernel/security/lsm` inside a privileged container, after `mount -t securityfs securityfs /sys/kernel/security`) reports only `capability,bpf` as active LSMs. **Landlock is not in the active LSM stack on this specific dev environment**, even though the syscalls exist — `landlock_restrict_self()` returns `ruleset=NotEnforced`, which the `landlock` crate treats as a graceful no-op (by design, so older kernels don't crash), not an error. This was confirmed to not be a seccomp issue either (`--security-opt seccomp=unconfined` made no difference). Confirmed by hand on this dev machine: `agent-init` still parses `readPaths`/`networkPorts` and logs the structured audit line correctly (both with and without those fields present, for backward compatibility with policy files written before this pass) even when the ruleset itself can't be enforced here.

This is expected to work correctly on:
- Most bare-metal Linux hosts (Landlock has been mainline since kernel 5.13, generally enabled by distros)
- GitHub Actions `ubuntu-latest` runners
- Real cloud VMs running modern Linux

**Before treating Phase 3 as passing any real security review, re-run `capability-enforcement.mjs` on one of those and confirm it logs `ruleset=FullyEnforced` (or `PartiallyEnforced`) and hard-asserts the traversal write is denied** — the script already detects which case it's in and only treats the denial as a required assertion when Landlock is actually active; on this dev machine it correctly reports "NOT VERIFIED (expected in this environment)" instead of a false pass or a false failure. The same applies to Test 5 (network deny-by-default, added alongside `networkUnrestricted`): the assertion only runs when `ruleset=FullyEnforced`/`PartiallyEnforced`.

**`capability-enforcement.mjs` covers considerably more than the write/read/network checks above.** In full, the script runs: Test 1 (write inside the declared path succeeds), Test 2 (write outside it via path traversal is denied), Test 3 (read inside the declared+baseline paths succeeds), Test 4 (read outside them via path traversal is denied), Test 5 (network is deny-by-default for an app declaring no `network:connect:*`), **Test 6 (symlink escape)** — a symlink planted *inside* the declared write/read path but pointing at `/opt` outside it is resolved by the kernel to its real target at syscall time and denied, exercised for both a write and a read through the symlink, proving the write/read-path grants can't be routed around by planting a link, **Test 7 (concurrent boundary stress)** — 20 in-scope and 20 out-of-scope writes fired at the same restricted process simultaneously via `Promise.all`, asserting every in-scope write still succeeds and, when Landlock is active, every single out-of-scope write is still denied, to catch any reordering or partial-completion bug in the app's own RPC dispatch that a serial test would never expose, **Test 8 (`BERTH_REQUIRE_ENFORCEMENT` fail-closed gate)** — see below, and **Test 9 (cross-app boundary isolation)** — two fixture apps (`boundary-app-a`/`boundary-app-b`) sharing one container and one bind mount, each scoped by its own independent `agent-init`/Landlock ruleset to only its own subdirectory, proving app A's write/read grant doesn't leak into app B's directory just because they share a container and a mount.

**Fail-open is the default; production should set `BERTH_REQUIRE_ENFORCEMENT` to flip it to fail-closed.** Everything described above is `agent-init`'s default behavior: if the Landlock ruleset can't be verified as enforced (or the capability policy JSON can't even be read/applied), it logs a warning and `exec()`s into the resident app anyway, unrestricted — this is what lets local dev keep working on a kernel like Docker Desktop for Mac's linuxkit VM that structurally can't enforce Landlock at all. Setting **`BERTH_REQUIRE_ENFORCEMENT=1`** (or `true`) in the container's environment flips that default: `agent-init` then refuses to `exec()` at all unless `restrict_self()` reported the ruleset status as exactly `FullyEnforced`, logging a distinct `capability_enforcement_refused` audit event (with the reason — either a non-`FullyEnforced` ruleset status, or the capability policy failing to apply in the first place) and exiting non-zero instead of silently running the app with the policy unenforced. **This is exactly what a production deployment should set** — fail-open exists only to keep non-enforcing dev environments unblocked, not because fail-open is ever the right posture once real enforcement matters. Test 8 verifies both branches from the same image, in a second container independent of Tests 1-7/9: with `BERTH_REQUIRE_ENFORCEMENT=1` set, it asserts the app still boots normally when the kernel can genuinely enforce the policy, and asserts a non-zero exit code plus the `capability_enforcement_refused` log line when it can't.

**A second, unrelated local-only limitation hit while adding deny-by-default network scoping:** rebuilding `agent-init`'s Docker layer fresh via `packages/docker-orchestrator`'s normal `buildImage()` path (a plain `docker build` from a tarred context, no bind mounts) hangs indefinitely on this dev machine — TLS handshakes to `index.crates.io` complete, but the response body never arrives, reproduced identically via plain `curl`/`cargo fetch` inside a bare `rust:1-alpine` container regardless of HTTP/1.1 vs HTTP/2, `--network=host`, or BuildKit vs the classic builder. The exact same request from this Mac's host (outside any container) succeeds in under 50ms. This points at a Docker Desktop virtual-network issue (likely MTU/PMTUD blackholing large HTTPS responses over the VM's bridge) specific to this machine, not a code or dependency problem — `agent-init`'s `Cargo.toml` didn't change, and every other `apk`/npm-registry fetch from inside a container this session worked normally.

Worked around it for real verification (not just type-checking) by bind-mounting the host's already-populated `~/.cargo/registry` into a plain `rust:1-alpine` container and building `--offline` — `cargo build --release --offline` succeeded cleanly (target `aarch64-unknown-linux-musl`, matching this image's actual arch), producing a real Linux binary with zero network access needed inside the container. Ran that binary directly (bind-mounted in, `BERTH_CAPABILITY_POLICY` pointed at three hand-written policy files: no network capability, `network:connect:*`, and a specific port) and confirmed real, correct behavior for all three: the audit JSON line reports the right `networkPorts`/`networkUnrestricted` in every case, the Landlock ruleset builds successfully with zero port rules in the deny-by-default case (no crash, no error — it just denies everything of that access type, as intended), and the process still `exec()`s into the downstream command correctly. Also confirmed `generate-capability-policy.js` produces the matching JSON for those same three manifests directly (no Docker needed for that half at all). This is real functional verification of the new logic, short of one thing: kernel-level *enforcement* still can't be observed here, since this Mac's Docker Desktop kernel doesn't have Landlock active in its LSM stack regardless (see above) — that part still needs CI or a real Linux host, same as the write/read-path checks always have.

### CI closes this gap

`.github/workflows/capability-enforcement.yml` runs this exact script on GitHub Actions `ubuntu-latest` on every push to `main`, every PR, and on demand via `workflow_dispatch`. Because that runner is a real Linux kernel (not Docker Desktop's linuxkit VM), `capability-enforcement.mjs` is expected to detect `ruleset=FullyEnforced` there and hard-assert the traversal write is denied. The script additionally treats a `NotEnforced` result as a hard CI failure (not just a warning) when `process.env.CI` is set — since Landlock going inactive on `ubuntu-latest` would itself be a real regression worth catching, not an expected environment limitation like on this Mac.

This closes the verification gap going forward: once this workflow has run green at least once on a real push, Phase 3's kernel enforcement claim is confirmed, and any future regression in `agent-init`'s Landlock ruleset construction gets caught by CI rather than silently reintroduced.
