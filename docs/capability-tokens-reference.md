# Capability Tokens Reference (Phase 3)

Phase 3 is the PRD's one kernel-level bet: turning `berth.yml`'s declared `capabilities:` into something the kernel actually enforces, not something an SDK politely checks before making a call on the agent's behalf.

## What's implemented

**`agent-init`** (`packages/agent-init`, Rust) sits between `entrypoint.sh` and whatever command it hands off to (the SDK runtime, `check-exports.js`, `npm test`, ...). It:

1. Reads a capability policy JSON (generated by `@berth/sdk`'s `generate-capability-policy.ts` from `berth.yml`, so the YAML/capability-glob parsing logic stays in one place — `@berth/manifest-schema` — instead of being reimplemented in Rust).
2. Builds a [Landlock](https://landlock.io/) ruleset restricting **write-ish filesystem access** (write, create, delete, rename — not read or execute) to only the paths declared via `filesystem:write:<path>` capabilities, plus a baseline of `/tmp`.
3. Calls `landlock_restrict_self()` on itself.
4. `exec()`s into the original command.

Landlock restrictions are inherited across `execve()` and can never be lifted — once applied, the resident app's runtime *and every process it spawns* are bound by them, enforced by the kernel at the syscall boundary. This is the PRD's actual differentiating claim: a compromised or misbehaving resident app can't write outside its granted paths because the kernel refuses the syscall, not because some SDK code declined to make the call.

**`requestCapability()`** (`@berth/sdk`) is real now, for the one dimension actually enforced: it checks whether a requested capability matches something declared in `berth.yml` (via `@berth/manifest-schema`'s `matchesCapability()`) and reports `{ granted, token }` honestly — but it doesn't *decide* anything the kernel hasn't already decided at process boot. See "What's deliberately deferred" below for what this doesn't cover yet.

## Why write-only, not read or network

- **Reads**: Node.js (and everything else in the base image) needs broad read access just to function — enumerating every path the runtime legitimately needs to read is fragile and would break in unpredictable ways across Node versions/OS layouts. Writes are both the higher-value threat-model boundary (tampering, exfiltration-by-write, planting files) and the one we could scope correctly without that fragility.
- **Network**: Landlock's network scoping (available since ABI v4 / kernel 6.7) restricts by **port**, not by domain — it can't express something like `browser:navigate:*.github.com`. Real domain-scoped filtering needs either a local proxy with SNI/Host inspection or an eBPF `cgroup/connect` hook with runtime DNS-resolution matching — both meaningfully bigger scope than this pass. Non-filesystem capabilities (`browser:*`, `github:*`, ...) are recorded in the policy and reported by `requestCapability()`, but not kernel-enforced yet.

## What's deliberately deferred (by explicit decision, not oversight)

- **Human admin approval flow.** The PRD's "human admins approve grants; agents never see raw secrets" describes an async approval workflow (a queue, a UI, someone clicking approve). Building that is its own sizeable feature. For this pass, `berth.yml`'s declared capabilities **are** the grant — enforced at boot, reported honestly by `requestCapability()` — with no human-in-the-loop step yet.
- **Real token lifecycle.** `requestCapability()`'s returned `token` is a hash tying the request to an app/capability/timestamp, not a cryptographically real, independently-verifiable, expiring token with its own audit trail.
- **Read and network path/domain scoping**, as above.
- **Per-syscall-denial audit logging.** `agent-init` logs the *policy it applied* at boot (visible in container logs) — that's a real audit record of what was granted, but not a live stream of every individual denied syscall. Real per-event audit logging needs either the Linux audit subsystem (`auditd`, needs privileges typically unavailable in an unprivileged container) or privileged eBPF LSM hooks — both out of scope here.

## Verification status — read this before trusting Phase 3 in any environment

**Verified:** the full pipeline runs correctly end-to-end via real Docker builds and containers (not just compiled) — `agent-init` builds inside Alpine, the capability policy JSON is generated correctly from `berth.yml`, `agent-init` runs and hands off to the runtime without breaking it (Node still starts, RPC still works, `berth test`/`berth dev` still pass), and `requestCapability()` correctly grants/denies based on declared capabilities (unit-tested).

**NOT verified — a real environment limitation, not a code defect:** actual kernel-level denial of a write outside a declared path. `packages/docker-orchestrator/test/capability-enforcement.mjs` is written to prove this (write inside `/workspace` succeeds; a path-traversal write to `/etc/...` gets refused with `EACCES`/`EPERM`) — but on Docker Desktop for Mac, the linuxkit VM's kernel (confirmed via `cat /sys/kernel/security/lsm` inside a privileged container, after `mount -t securityfs securityfs /sys/kernel/security`) reports only `capability,bpf` as active LSMs. **Landlock is not in the active LSM stack on this specific dev environment**, even though the syscalls exist — `landlock_restrict_self()` returns `ruleset=NotEnforced`, which the `landlock` crate treats as a graceful no-op (by design, so older kernels don't crash), not an error. This was confirmed to not be a seccomp issue either (`--security-opt seccomp=unconfined` made no difference).

This is expected to work correctly on:
- Most bare-metal Linux hosts (Landlock has been mainline since kernel 5.13, generally enabled by distros)
- GitHub Actions `ubuntu-latest` runners
- Real cloud VMs running modern Linux

**Before treating Phase 3 as passing any real security review, re-run `capability-enforcement.mjs` on one of those and confirm it logs `ruleset=FullyEnforced` (or `PartiallyEnforced`) and hard-asserts the traversal write is denied** — the script already detects which case it's in and only treats the denial as a required assertion when Landlock is actually active; on this dev machine it correctly reports "NOT VERIFIED (expected in this environment)" instead of a false pass or a false failure.

### CI closes this gap

`.github/workflows/capability-enforcement.yml` runs this exact script on GitHub Actions `ubuntu-latest` on every push to `main`, every PR, and on demand via `workflow_dispatch`. Because that runner is a real Linux kernel (not Docker Desktop's linuxkit VM), `capability-enforcement.mjs` is expected to detect `ruleset=FullyEnforced` there and hard-assert the traversal write is denied. The script additionally treats a `NotEnforced` result as a hard CI failure (not just a warning) when `process.env.CI` is set — since Landlock going inactive on `ubuntu-latest` would itself be a real regression worth catching, not an expected environment limitation like on this Mac.

This closes the verification gap going forward: once this workflow has run green at least once on a real push, Phase 3's kernel enforcement claim is confirmed, and any future regression in `agent-init`'s Landlock ruleset construction gets caught by CI rather than silently reintroduced.
